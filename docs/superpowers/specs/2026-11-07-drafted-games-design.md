# Next in queue: 1–3 drafted games and shared player view

Date: 2026-11-07. Owner accepted independent courts and requested 1–3 upcoming drafted games selected by queue master, plus QR visibility of queue/current games. Owner explicitly approved waiting-only reservations, fixed teams, FIFO to whichever court opens next, fewer drafts when people are insufficient. Preserve all existing uncommitted work. No release/backend-settings authorization.

## Design
Add a shared Next in queue section with numbered fixed-team games, singles/doubles and names. Queue master chooses 1–3 games to add, maximum three pending total; appends keep existing lineups, and Clear upcoming games releases all reservations. Build as many as can be formed under queue/skill/partner rules and explain partial results. Never use an active player, or put someone in two drafts. Drafting reserves but does not count as play, alter standings/waits, start a swap timer, or record teammate history. The first draft starts atomically on any finished/ready court; others stay ordered. Current games remain independent.

Reserved players are excluded from normal starts, replacement candidates and drag swaps; Players shows their draft position. A break/removal or reopening an old result invalidates any affected draft as a whole, releases its other players and displays a notice. Type/partner-limit changes clear pending games with explanation; court-count changes preserve drafts (not court-specific). Skill/record changes do not silently redraw announced teams. Manual Play next picks feed draft generation, are consumed once reserved, and cannot steal someone already reserved. Preserve waiting order between unrelated updates; manual picks then longest wait, ties fixed/randomized on entry. Show waiting players not already in drafts as the public queue.

## Persistence and compatibility
Public domain schema becomes v3 with queuedGames (id, matchType, sideA/B player IDs) and waitingPlayerIds. Migrate v1/v2 and retain players, IDs, records, active games/timestamps, share credentials, existing local keys and game-day settings. Validate max three drafts, side sizes, uniqueness, active membership, and no overlap with unfinished games. Serialized v3 public/backup data includes drafts/queue but never edit token or organizer settings. Existing RPC JSON storage requires no SQL/hosting changes.

All new readers accept legacy payloads; older React readers reject v3. Do not publish v3 behind an old deployed viewer. Local live tests use this updated viewer; release needs an updated app/reader at the sharing origin and owner authorization. Old QR sessions remain readable by the new app. Share links using this computer’s loopback address cannot open on phones; show a useful notice and validate the actual network-origin link on the local LAN. No deployment inferred.

## Implementation boundaries
Use a separate domain queue module with pure validation/reconciliation and engine drafting/starting. Rename internal state types to SessionState/SerializedSessionState as v3 replaces the v2-only shape. Keep schema-version tests aligned with intentional v1/v2→v3 migration. State-store reconciliation creates a new public-session reference when queue metadata changes, so existing sync subscription publishes queue changes too. Shared viewers see Next in queue/current courts/waiting order without draft/start/cancel controls. Preserve stable per-court identity and all-four rotation.

Randomized invariant includes queued + unfinished assignments. Browser phone/tablet/desktop: queue-master flow and read-only viewer. Live Supabase create/update/read, queue-order publication, draft→active update within about17s, actual QR contents decode to correct network viewer URL and no edit controls. Update both handoffs and local-only usage record. Stop if five-hour remaining <=10%.
